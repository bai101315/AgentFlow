## 1. 并发与并行

- 并发：多个任务在一段时间内交替推进，不要求同一时刻执行。
- 并行：多个任务在同一时刻分别在多个计算核心上执行。

单线程事件循环可以实现并发，但通常不能让纯 Python CPU 代码多核并行。

## 2. 进程、线程与协程

| 对象 | 调度者 | 资源关系 | 开销 | 典型场景 |
|---|---|---|---|---|
| 进程 | 操作系统 | 地址空间相对独立 | 较大 | CPU 密集、故障或权限隔离 |
| 线程 | 操作系统 | 共享同一进程大部分资源 | 中等 | 同步阻塞 I/O、同步 SDK |
| 协程 | 用户态事件循环；承载线程仍由 OS 调度 | 共享所属线程和进程资源 | 较小 | 大量网络 I/O、数据库、SSE |

同一进程中的线程共享：代码段、全局数据、堆、打开的文件描述符等。线程独享：程序计数器、寄存器上下文、线程栈、线程局部存储、线程 ID。

## 3. 理解协程

用“一名服务员服务多桌客人”理解：服务员是一条线程，每桌流程是一个协程，等待厨房是等待 I/O。某桌等待时，服务员去处理其他桌；事件循环负责安排哪个协程继续运行。

核心：协程重叠的是 I/O 等待时间，不是把 CPU 计算加速。

```python
import asyncio

async def ask(name):
    print(name, "start")
    await asyncio.sleep(2)
    print(name, "end")

async def main():
    await asyncio.gather(ask("A"), ask("B"), ask("C"))

asyncio.run(main())
```

三个任务各等待约 2 秒，总时间接近 2 秒。

### `async def`、协程对象和 `await`

- 调用 `async def` 函数得到协程对象。
- 协程需要被 `await`、包装为 Task 或交给事件循环调度。
- 当所等待操作未完成时，当前协程可暂停并把控制权交还事件循环。
- `await` 不等于创建线程，也不是所有 `await` 都必然发生切换。

同步阻塞代码会卡住事件循环：

```python
async def bad():
    time.sleep(10)
```

等待操作应使用异步 API；同步阻塞 SDK 可使用 `asyncio.to_thread()` 或受控线程池。

## 4. GIL

GIL 是 CPython 的全局解释器锁。在传统启用 GIL 的 CPython 中，同一解释器进程内通常只有一个线程能在某一时刻执行 Python 字节码。

### GIL 限制什么

典型纯 Python CPU 密集型多线程难以通过多个线程同时执行字节码来利用多个 CPU 核，线程竞争和切换还可能增加开销。

### GIL 不限制什么

- 不禁止创建多个操作系统线程。
- 不禁止线程并发。
- I/O 等待时线程通常会释放 GIL。
- 不阻止多进程各自使用独立解释器和 GIL。
- 原生扩展可能释放 GIL 或使用底层线程/GPU。
- 不自动保证业务共享状态线程安全。

版本边界：现代 CPython 有可选 free-threaded 构建；常规面试通常讨论传统启用 GIL 的 CPython，回答时应明确边界。

## 5. 线程池、进程与容器

### 线程池

维护有限数量的工作线程。任务进入队列，空闲线程执行，完成后继续复用。它避免频繁创建/销毁线程，并限制线程总量。

长期不返回的任务会占满线程池；线程数不是越多越好，还要考虑内存、上下文切换、下游连接池和服务承载能力。

### 独立进程

拥有相对独立的虚拟地址空间。进程通信通常使用管道、队列、共享内存、Socket、数据库或消息队列。适合 CPU 密集或需要故障隔离的任务。

### 容器

容器是操作系统级隔离与部署方式，内部最终运行进程。它利用 namespace、cgroup 等机制提供文件系统、网络、进程视图和资源限制。普通子进程或默认容器都不自动等于安全沙箱。

## 6. 任务选型决策

```text
主要等待网络、数据库或磁盘？
  是 -> 有原生异步 API？
          是 -> 协程
          否 -> 受控线程池 / asyncio.to_thread
  否 -> 是典型纯 Python CPU 密集任务？
          是 -> 多进程 / 任务队列
          否 -> 分析原生扩展、GPU 和实际运行模型

需要隔离不可信代码？
  -> 独立进程 + 沙箱/容器 + 权限、网络、文件和资源限制
```

| AI 场景 | 优先方案 | 原因 |
|---|---|---|
| 100 个异步 LLM 请求 | 协程 | 网络 I/O 等待多 |
| 异步 FastAPI 调同步 SDK | 线程池/`to_thread` | 避免阻塞事件循环 |
| 大量 SSE 连接 | 协程 | 大量连接多数时间在等待 |
| 纯 Python 图像复杂计算 | 多进程 | 绕开单进程 GIL并利用多核 |
| 不可信工具执行 | 受限沙箱/容器中的独立进程 | 需要权限和资源隔离 |

## 7. AI 服务中的完整执行层次

一个程序启动后通常至少对应一个进程，但线程和协程不会自动大量创建，需要代码或框架主动创建：

```text
一个服务进程 P
    |
    +-- 事件循环线程 T1
    |       +-- 协程 C1：权限服务
    |       +-- 协程 C2：向量数据库
    |       +-- 协程 C3：LLM 流式输出
    |
    +-- 线程池工作线程：同步 SDK、阻塞文件 I/O
    |
    +-- 子进程/进程池：纯 Python CPU 计算或隔离任务
```

典型 AI 问答流程：请求进入服务进程后，事件循环线程创建 handler 协程；权限查询和向量检索协程分别在网络 `await` 处挂起；事件循环在 socket 就绪时恢复对应协程；两者完成后发起 LLM 请求；SSE 协程逐段发送 token；完成或客户端断开时取消下游任务并在 `finally` 中清理资源。

如果 SDK 只有同步方法：事件循环线程执行 `await asyncio.to_thread(sync_call)`，线程池工作线程执行阻塞调用，结果返回后原协程恢复。`to_thread` 是把阻塞工作移出事件循环，不是把同步函数本身变成原生异步 I/O。

### 层级关系图

```text
进程：资源隔离和运行环境
  |
  +-- 事件循环线程：协程调度器
  |     +-- handler 协程
  |     +-- 向量检索协程
  |     +-- LLM/SSE 协程
  |
  +-- 线程池：管理一组线程，执行同步阻塞任务
  |
  +-- 子进程/进程池：执行 CPU 密集任务或隔离任务
```

事件循环不是进程，也不是一次调用；它是运行在线程中的调度器。线程池不是整个进程的线程总管，只管理自己创建的工作线程。不是每个线程都必须运行协程，只有运行事件循环的线程才会调度协程。

异步接口调用同步 SDK 时，真正的问题是同步调用直接占用了事件循环线程。`async def` 不会自动把内部普通函数变成异步；应使用原生异步 SDK，或用 `asyncio.to_thread()`/线程池把同步阻塞调用移出事件循环。

子进程是父进程创建的独立进程，拥有自己的地址空间、解释器和 GIL，适合典型纯 Python CPU 密集任务或故障/权限隔离，但需要通过 IPC 交换数据，并承担启动、内存和序列化成本。

## 8. GIL 的取舍与优化

### 优点

- 简化 CPython 解释器内部并发控制。
- 保护解释器内部状态，降低实现复杂度。
- 历史上有利于 C 扩展生态兼容。
- I/O 等待时通常可释放，不妨碍典型 I/O 并发。

### 缺点

- 传统 CPython 中纯 Python CPU 密集线程难以多核并行。
- 线程竞争和切换可能增加开销。
- 容易让开发者误以为不需要业务锁，实际仍可能发生竞态。
- 利用多核通常需要多进程，带来内存、启动、序列化和通信成本。

### 优化方向

- I/O 密集：原生异步客户端 + 协程。
- 同步阻塞 SDK：受控线程池或 `asyncio.to_thread()`。
- 纯 Python CPU 密集：多进程、任务队列或原生扩展。
- 数值/模型计算：根据 NumPy、PyTorch、GPU 是否释放 GIL 和实际瓶颈选择方案。
- 服务治理：连接池、Semaphore、超时、限流、取消和可观测性。

CPython 社区有 free-threaded/no-GIL 构建方向，但不能简单理解为升级后所有代码自动变快，还要考虑 C 扩展兼容、锁竞争、内存和生态迁移。

## 9. Python 与 CPython

Python 是编程语言，包含语法、语义和标准库接口；CPython 是 Python 的一种实现，主要用 C 编写，也是最常用的实现。PyPy、Jython 是其他实现。

GIL、引用计数等通常是 CPython 实现细节，不应说成所有 Python 实现都必然如此。面试时先说语言层面的保证，再明确“在传统启用 GIL 的 CPython 中……”的实现边界。

## 易错点

1. 协程不等于并行，也不会自动加速 CPU 计算。
2. `async def` 里调用同步函数不会自动变成异步。
3. 事件循环不是进程，而是线程中的协程调度器。
4. 线程池不是整个进程的线程总管，只管理自己的工作线程。
5. 不是每个线程都有协程，协程必须由事件循环调度。
6. GIL 不等于禁止并发，也不等于业务线程安全。
7. 容器不是 Python 的并发模型，也不是天然绝对安全。
8. “CPU 用进程、I/O 用协程”是起点，不是无条件规则；原生库、GPU、SDK 能力和部署模型都会改变选择。

## 面试表达

典型 CPython 中，纯 Python CPU 密集任务通常使用多进程，高并发 I/O 优先使用协程，同步阻塞接口可放线程池。GIL 限制同一解释器内多个线程并行执行 Python 字节码，但不禁止线程并发；线程等待 I/O 时通常会释放 GIL。AI 服务常采用混合方案：LLM 和向量库请求用协程，同步 SDK 用线程池，CPU 工作用多进程，不可信工具放受限沙箱。
