## 1. TCP 基本特性

TCP 是传输层协议，提供面向连接、可靠传输、字节流服务。可靠性不只是三次握手，还依赖序列号、确认、重传、窗口等机制；这些内容后续单独学习。

## 2. 三次握手

```text
客户端                                服务端
  | -------- SYN, seq=x ------------> |
  | <----- SYN+ACK, seq=y, ack=x+1 -- |
  | -------- ACK, ack=y+1 ----------> |
```

1. 客户端发送 SYN，并携带初始序列号 `x`。
2. 服务端返回 SYN+ACK：确认客户端序列号 `x+1`，并发送自己的初始序列号 `y`。
3. 客户端返回 ACK，确认服务端序列号 `y+1`。

握手建立双方连接状态并同步初始序列号，使双方确认报文往返路径能够工作。

## 3. 为什么不能简单两次握手

如果服务端在第二步后就认为连接完全建立，它无法确认客户端是否收到自己的 SYN+ACK。旧的、延迟到达的 SYN 还可能让服务端为一个已经失效的请求建立状态和分配资源。

第三次 ACK 让服务端确认客户端已经收到服务端的 SYN 和初始序列号。

## 4. 面试表达边界

“确认双方收发能力”是常见面试概括，但最好结合序列号和状态同步解释，不能只背一句口号。

三次握手不能单独保证后续所有数据永远可靠；后续数据可靠性还依赖确认、重传、校验、排序和窗口机制。

## 易错点

1. 三次握手发生在 TCP 层，不是 HTTP 协议本身。
2. HTTPS 通常先建立 TCP，再进行 TLS 握手；HTTP/3 基于 QUIC/UDP，是另一个边界。
3. 第三次握手的 ACK 报文可以携带应用数据，但握手状态要按协议理解。
4. 不要把三次握手解释成“客户端说一次、服务端说一次、客户端再客气一次”。核心是连接状态和序列号确认。

## 面试表达

TCP 三次握手用于建立双方连接状态并同步初始序列号。客户端先发送 SYN，服务端返回 SYN+ACK，客户端再返回 ACK。两次握手无法让服务端确认客户端收到了服务端的 SYN 和序列号，旧 SYN 延迟到达时还可能导致服务端建立无效连接并浪费资源。

## AI 应用开发关联

- 调用远程 LLM API 通常依赖 TCP/HTTPS 连接。
- 连接池和 HTTP Keep-Alive 可以复用连接，减少重复建连成本。
- SSE 是 HTTP 长连接流式响应，其稳定性依赖底层传输连接。
